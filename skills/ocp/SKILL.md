# Managing the agent setup with OCP

OCP renders one source (a folder with `ocp.yaml`) into OpenCode, Claude Code and Codex, on every machine the user syncs. A change made directly in a harness's own files stays on that harness and machine. If OCP owns that file, the next apply reports the edit as drift. Make changes in the source.

## 1. Find the source

```sh
ocp status --json
```

- `config_file` is the file to edit. `machine` is this machine's name. `harnesses` lists the targets, and `active` shows each harness's profile.
- If the command is missing or says "OCP is not set up", there is no source. Edit the harness directly and mention that OCP could manage it.
- Never edit generated files:
  - `~/.config/opencode` is a link to a rendered release.
  - In `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`, never touch the block between `<!-- BEGIN OCP MANAGED -->` markers.
  - Skills, agents and settings that OCP installed are also generated.

## 2. See what applies now

```sh
ocp show --json          # every profile, with where each entry comes from
ocp show <profile>       # one profile, readable, with its context cost
```

## 3. Put the change in the right place

| The change should apply to | Edit |
|---|---|
| every profile, every machine | root `ocp.yaml` |
| one profile | `profiles/<name>/profile.yaml` (or `profiles/<name>.yaml`) |
| one machine only | a `machines: { <machine>: {...} }` overlay, at the root or in a profile |
| profiles that exist on some machines only | `hosts: [<machine>]` on the profile |

A machine overlay only takes effect on that machine. Applying it anywhere else changes nothing; `ocp show` lists it with its machine name, which confirms the change.

The root file, profiles and machine overlays all accept `config`, `claude`, `codex`, `instructions`, `skills`, `plugins` and `agents`. A profile also takes `extends: <parent>`. Unknown keys are errors.

**Skills.** These are listed by name. Folder names do not enable anything.

```yaml
skills:
  - stop-slop                              # local: skills/stop-slop/SKILL.md
  - github:owner/repo//skills/pdf          # one folder of a repository
  - github:owner/repo//skills/pdf@v1.2     # pinned to a tag or commit
```

`ocp apply` locks a new Git skill to a commit in `ocp.lock`, which needs network access. `ocp.lock` is part of the source: commit it, or let `ocp sync` do so.

**MCP servers** use OpenCode's format under `config`. OCP translates them for Codex. It does not install any of them into Claude Code yet, and prints one warning per server on every apply; that warning is expected.

```yaml
config:
  mcp:
    servers:
      playwright:
        type: local
        command: [npx, -y, "@playwright/mcp@latest"]
      figma:
        type: remote
        url: http://127.0.0.1:9300/mcp
        headers:
          Authorization: "Bearer {env:FIGMA_TOKEN}"
```

**Secrets.** Never write a key or token into the source. Use `{env:NAME}` or `{file:~/path}`, and OCP reads it when it is needed.

**Models.** Set models in `config.model`, never in `claude:` or `codex:` as well (setting both is an error). A plain `provider/model` string is used as is by OpenCode, and Claude Code or Codex accept it only for a provider they understand. To set each harness's model explicitly, use a mapping:

```yaml
config:
  model:
    opencode: zai/glm-5.1
    claude: glm-5.1
    codex: gpt-5.5
```

**Providers.** For OpenCode, use `config.provider`. Each other harness takes its own block, because their endpoints speak different protocols:

```yaml
claude:                       # ~/.claude/settings.json
  env:
    ANTHROPIC_BASE_URL: https://api.z.ai/api/anthropic
  apiKeyHelper: "{ocp} secret print '{file:~/.config/zai/key}'"
codex:                        # ~/.codex/config.toml
  model_provider: myproxy
  model_providers:
    myproxy: { name: My proxy, base_url: "http://127.0.0.1:4000/v1", env_key: MYPROXY_KEY }
```

- `claude:` accepts `env`, `apiKeyHelper` and `model`.
- `codex:` accepts `model`, `model_provider`, `model_providers` and `model_reasoning_effort`. Codex only speaks the Responses API.

**Agents and instructions.**

```yaml
instructions: [guides/style.md]       # paths relative to the source
agents:
  reviewer:
    file: agents/reviewer.md          # Markdown with a description in its frontmatter
    model: { opencode: openai/gpt-5.5, claude: sonnet, codex: gpt-5.5 }
```

## 4. Apply

```sh
ocp apply --preview      # what would change, per harness; writes nothing
ocp apply                # render and activate on this machine
ocp sync                 # also commit, pull and push when the source is a Git repo
```

- If `apply` reports that generated files have drifted, someone edited a rendered file. Move that edit into the source first. Only then run `ocp apply --force`, which overwrites the drifted files.
- If it says a setting or table "was edited outside OCP" or "is not owned by OCP", a harness file conflicts with what OCP owns. Explain the conflict to the user. There is no force option for it.
- To see whether a profile has grown too large, check its context estimate with `ocp show <profile>`. Add a large skill set to one profile rather than to the root.
- Do not run `ocp reset` unless the user asks for it. It detaches OCP from every harness.
